# TTLock / TTHotel 自助入住接入设计

日期：2026-10-15。用户提供官方接口作为门锁候选。本轮仅文档调查和架构设计，未获取凭据、调用设备API、生成密码、远程开锁或发送消息。

## 官方证据与限制

原始入口：https://cnopen.sciener.com/document/doc?urlName=example%2FTTHotelIntegration.html （当前网页读取工具无法直接打开动态入口）。通过搜索读取官方同主题静态文档及入门页：

- https://cnopen.sciener.com/documentPages/htmlPages/example/TTHotelIntegrationEn.html
- https://euopen.sciener.com/documentPages/htmlPages/userGuide/getStartedEn.html

核实的能力：密码、eKey、远程开锁及记录接口；自定义密码和远程操作有联网条件。TTHotel管理员可从客户端对接设置取得集成参数，和TTLock App开放平台申请路线不同。TTHotel示例要求使用导出的集成认证数据，不把正式登录密码当作导出字段，避免重复MD5处理。实际区域端点及账号归属待核实，不照抄示例域名用于马来西亚设备。

官方入门页说明无公共测试账号/沙箱；初期使用本地模拟适配器。设备写入测试需另外准备已授权、未服务真实住客的测试锁。文档可用不等于现有设备已经兼容或已接通。

## PMS业务设计（拟议，非厂家承诺）

自助入住流程：订单验证 → 客人提交所需资料 → 按运营规则审核/支付条件校验 → 明确分房分床 → 确认清洁与维修状态 → 建立对应门禁授权任务 → 确认设备授权结果 → 客人通过受控页面获取权限。表单提交成功不等于已入住或授权成功；开门记录也不自动证明客人已完成入住。

共用房门不等于每床一把锁：分别建门店入口、楼层、宿舍门、独立房门及可选储物柜资源。床位分配映射到必要门禁集合；同一宿舍可由多笔订单授权，退一人只撤销本人的授权，不删除同房其他客人的权限。不得为了方便向所有住客发同一个长期共享密码。

新增领域实体：

- LockConnection：组织/门店、供应商、区域、密钥引用和能力快照。
- AccessPoint / LockBinding：入口类型、设备ID、房间或公共区域映射及版本。
- AccessGrant：订单、住客、分配版本、门禁集合、开始/结束时间、授权类型、外部授权ID及状态。
- AccessJob / AccessEvent：幂等任务、执行/回执、失败原因、脱敏审计及补偿记录。

状态：requested → provisioning → active → revoke_pending → revoked；failed和unknown分别表示失败或结果不确定。API已接受但锁是否生效不明确时不能展示“已撤销”。令牌和密码只经服务端保管，页面不接触clientSecret，普通日志不保存开门凭据。所有门锁操作需校验门店权限、有效分配与版本，记录触发人及原因。

换房/换床先区分是否改变门禁集合。同房换床通常不需新发房门权限；跨房需检查新授权可用、处理旧权限撤销并记录生效顺序。实际无法原子完成多锁操作，必须显示部分失败并由运营处理，不能用本地数据库回滚假装设备也回滚。

续住必须核实延长权限成功；提前退房/取消需要显式撤销任务；断网时撤销可能无法即时生效，按授权类型与设备能力提供现场处理方案。离线密码仅在已验证规则下使用，不假定支持即时撤销。不得通过重试无意重复生成多套有效权限。

## 实施门槛

先确认：实际使用TTLock还是TTHotel、门锁型号/固件、按门店的设备清单、网关或Wi-Fi覆盖、公共门与房门布局、账号数据区域、集成授权及费用。初步选择短期密码、eKey或房卡方案后，再逐项核对创建/修改/撤销/查询的接口契约与时间单位。不要混用云端发卡和本地发卡器流程，需另核对其兼容规则。

接入顺序：模拟器与业务条件测试 → 服务端密钥配置 → 只读设备列表及映射 → 单把测试锁授权闭环 → 续住/换房/提前退房/断网恢复 → 人工验收后另行确认生产启用。发送客人消息、调用真实锁均不在本轮授权内。

验收至少覆盖：重复任务、超时结果不明、撤销离线、换房部分失败、多人共住宿舍、到期边界、门店越权、分配变更后的旧任务、低电量/网关离线、日志脱敏。开锁/撤销动作必须按实际设备确认，不能仅凭HTTP成功判定。
