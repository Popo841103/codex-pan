# 库存与领域模型

状态：设计草案，尚无数据库迁移或生产库存。运营日期使用门店时区，首店拟用Asia/Kuala_Lumpur；事件时间存UTC。住宿区间为[入住日期, 退房日期)，相邻退住不冲突。

## 实体和约束

所有业务实体包含organization_id；门店内实体包含property_id，以组合外键阻止跨店关联。ID不可由展示房号代替，房号/床号在店内限定范围唯一，可停用但不得删除历史引用。

| 实体 | 核心内容及关系 |
| --- | --- |
| Organization / Property | 组织、门店、时区、币种与政策版本 |
| RoomType / Room / Bed | 房型、物理房间、房内床位、位置和有效期；房床均可设分区限制 |
| SellableProduct / InventoryPool | 按房或按床的销售产品、所属门店、库存池和适用资源；床产品可表达性别区和规格 |
| PhysicalResource / ProductResource | 物理冲突最小单元及产品资源映射；整房产品占该房全部单元，床产品占对应单元 |
| Reservation / ReservationItem | 订单主档与多条房型/床型数量、入住区间、政策和金额快照；一个订单限定一家门店 |
| InventoryCommitment / InventoryDay | 逐日需求（暂留/确认/在住）、池容量/停用及版本；未分配订单仍有需求 |
| Guest / ReservationGuest | 客人、订单关联、与分配相关的经确认资料；不从姓名推测性别 |
| Assignment / Occupancy | 每个销售单位及住客的分配时间段、真实入住/退房事件；数量和日期须被订单覆盖 |
| ResourceBlock / HousekeepingTask | 房/床停用区间及原因；清洁任务状态与可售状态分开 |
| Charge / Payment / Refund / SecurityDepositEntry | 费用、收款、退款、押金独立账；记录手工凭证或第三方交易ID |
| AuditEvent / ChannelMapping / Inbox / Outbox | 操作审计、渠道外部ID、去重入站及可靠出站 |

物理单元是排他占用边界，不是销售数量：私房一个单元可住两人但仅算一间库存；宿舍每床一个单元。未来整间宿舍产品映射全部床单元，而非新增独立容量。床/房布局变更使用生效日期，不能重写历史入住资源。

## 库存计算与分配可行性

单一独立库存池可售夜数 = 有效容量 − 维修/销售停用容量 − 有效暂留需求 − 确认及在住需求。分配只是把已有需求落到资源上，不再扣第二次库存。取消、过期暂留、缩短住宿必须在同一事务释放相应日期需求。

多个产品共享物理资源时，禁止分别相减独立售卖。每次确认或变更必须验证全部受影响日期的资源可行性，包含未分配订单、分区、同房和连续住宿约束。只满足逐日总量并不代表有可连续入住的床。

建议首期在店内锁定相关库存日期行，按固定顺序获取锁；使用确定性匹配为所有受影响订单计算内部资源预留，人工未分配时不展示为已分床。默认每个住宿单位全程同一资源；需要中途换床时显式拆分区间，禁止优化器自动移动已入住或人工锁定分配。强制同房按组求解，尽量同房仅作评分项。匹配无解就返回具体冲突，不靠前端总数判断。规模扩大后可替换求解器，保留同一契约。

数据库存每资源每营业日唯一有效占用，或用PostgreSQL排斥约束禁止资源区间重叠；内部预留与人工分配指向同一占用记录，防止互相重复计算。日内实际入住/换床另存时间段；同日换床的已使用床位保留待清洁状态，不能因夜间预留释放就直接入住他人。

暂留具有expires_at；定时任务过期释放与确认事务采用同一锁，确认时再次检查到期，不依赖后台任务准时运行。默认不允许手工超售。OTA迟到订单如已无法容纳，应持久化为“渠道冲突待处理”并告警，不能丢弃订单或伪造可分配状态。

## 关键状态转换

- 订单：draft → held → confirmed → completed；取消、过期、no_show是带原因的分支。是否收费及库存释放由政策决定；draft不占库存。
- 住宿单位：unassigned → assigned → checked_in → checked_out；团体支持部分入住退房，整单状态从各单位汇总。
- 财务：费用、实收、已退、押金分别汇总；订单取消不等于退款成功，付款成功也不自动入住。
- 清洁：clean → dirty → cleaning → clean；维修区间独立记录，修好不自动视作清洁完成。

## 原子操作

创建确认订单：校验权限/幂等键 → 锁相关日期 → 校验最新容量及匹配 → 写订单、需求、内部预留 → 写审计与outbox → 提交。唯一键限制组织内幂等键，并保存请求摘要，防同键不同内容。

换床：锁订单与新旧资源/日期 → 校验目标分区、同房及清洁维修 → 截断原分配并新增目标段 → 调整受影响预留与清洁任务 → 写理由、审计、outbox → 提交。失败全部回滚。跨房型或销售产品变更需明确重算库存和费用，不能只修改床号。

维修停用：先列受影响内部预留、已分配和在住单位，正常操作拒绝冲突；需先显式搬迁/处理订单，再建立停用。紧急事故走单独有权限的事件记录和待处理流程，不静默取消客人住宿。

退房：保存实际离店时间、结算及押金决定 → 结束实际占用 → 转待清洁。提前退房是否释放剩余夜数需明确选择及政策记录；退房不抹去已消费夜数。

## 必须通过的库存场景

1. 同一最后床位两个并发订单，仅一个确认；请求重放不新增需求。
2. 未分配两床订单减少两床库存，随后分床不再扣库存。
3. 相邻日期可续用，跨午夜和门店时区正确；同日未清洁不得入住。
4. 整间宿舍与其中任何床互斥；不同产品不能重复出售同一物理单元。
5. 每天总数有余但没有连续床位时，默认拒绝，显式换床方案才可接受。
6. 三人强制同房而只剩跨房三床时拒绝；偏好同房时提示需拆组。
7. 换床目标已占用/维修/分区不符时原分配与库存完全保持。
8. 暂留到期与确认并发、取消与回调重放均不产生负库存。
9. 房级维修覆盖全部床；床级维修不重复扣整房容量。
10. 部分退房、续住、提前离店保留历史；跨店ID引用及无权限写入被拒绝。
